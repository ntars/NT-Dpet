## 一、这是什么

NT-Dpet 是一个**桌面伴侣软件**。它不是一个聊天窗口加一层皮肤，而是一套把「她」拆成可维护部件的实现：情绪会随时间回落，记忆会分层沉淀，主动性有节制，声音和形象可以替换，而且数据默认全部留在你自己的机器上。

技术上，它是 [DeepSeek-Harness](https://github.com/deepseek-ai/deepseek-harness)（下称 DSH）的**发行版**，不是独立框架。

DSH 相当于内核：插件树、模型调用、会话与工具链。NT-Dpet 相当于一套发行套件：不重写内核，只负责三件事——

1. **装配**：把人格、记忆、情感、通道、声音、行动装成一个能跑的整体
2. **看住**：任何一个环节失效，其余部分照常工作
3. **兜底**：增强能力失败时退回基础能力，不把报错抛给用户

### 它不是什么

| 不是 | 原因 |
|---|---|
| 自研大模型 | 只做接入，模型由用户选择与提供 |
| 协议逆向 | 只使用现成协议端，不做破解 |
| 又一个插件市场 | 做整装组合包，不做零件货架 |
| 无风险产品 | 个人号通道存在封禁风险，如实标注，不做美化 |

## 三、核心设计

以下六条是这个项目与「聊天窗口套壳」的区别所在。每条都注明实现状态——**设计已定不等于已经能跑**。

### 3.1 情绪会自己回落，不是一个滑块

`[已实现]` `@nt-dpet/emotion`

情绪分五维，归属两类：

| 维度 | 归属 | 含义 | 初始值 |
|---|---|---|---|
| `mood` | 实例全局 | 此刻心情 | 0.5 |
| `energy` | 实例全局 | 此刻精力 | 0.7 |
| `affection` | 按人 | 对某人的好感 | 0.1 |
| `trust` | 按人 | 对某人的信任（慢涨快跌） | 0.1 |
| `intimacy` | 按人 | 与某人的亲密 | 0.0 |
| `familiarity` | 按人 | 熟悉度，决定注入多少画像 | 0.0 |

**回落用指数曲线，不是线性**：

```
v(t) = 基线 + (当前值 − 基线) × e^(−λt)
λ = ln2 / 半衰期
```

四档半衰期：1 小时 / 4 小时（默认）/ 12 小时 / 不回落。选指数而非线性，是因为人的情绪「刚开始淡得快、越久越淡」；线性会在某一刻突然归零，很假。

**三个实现细节**：

- **惰性回归**：不靠定时器推进时间，而是每次读取时按「距上次更新过了多久」现算。好处是进程崩溃重启不需要补偿计算——不会因为挂了 3 小时，回来就算出一个离谱的值
- **弥散**：心情会迁怒到别人头上。对某人的偏移 = `(mood − 基线) × 0.4 × (1 − familiarity × 0.5)`。这条是反直觉的：**越不熟越容易被殃及**，因为不熟的人，她没理由为他区分「这不是你的错」
- **落盘**：关系跨过 0.25 / 0.50 / 0.75 任一档位立即落盘，其余情况每 60 秒批量落盘。崩溃最多丢 60 秒

换人格时五维**全部保留**——人格是皮肤，不是另一个角色。

### 3.2 主动性有拒绝权，也有沉默衰减

`[设计已定，未实现]` `@nt-dpet/proactive`

主动消息过三道闸门，顺序固定，前一道不过则后面不计：

| 闸门 | 回答的问题 | 判据 |
|---|---|---|
| 一、时机 | 现在该醒吗 | 作息窗口内 + 距上次主动 ≥ 冷却时长 + 拒绝权判定 |
| 二、话由 | 有值得说的吗 | 记忆里有未消化的事 / 情绪偏离基线 / 时间性事件 |
| 三、分寸 | 说了会不会打扰 | 今日额度 > 0 + 不在静默时段 + 用户不在忙碌中 |

**四个不那么显然的选择**：

- **随机时刻醒，不定整点**。整点会有机械感——「又到十点了，她该说话了」；随机时刻更像「她刚好想起你」
- **拒绝权**：即使三道闸门全过，仍有 30% 概率今天就是不主动。一个永远按规则开口的东西不叫性格，叫会说话的闹钟
- **沉默衰减**：连续 3 天没被回应，额度开始下降；第 7 天归零，不再主动分享。但**日记照写**。这不是限流（「少打扰你」），而是她察觉你没接话、慢慢把心事收回去。哪天主人主动开口，额度立刻复位
- **双视角日记**：给主人的那本有细节有情绪，给自己的那本不加滤镜。有人看着的时候写不出真话；诚实的那本才是长期记忆的原料

### 3.3 她怎么叫你，跟着关系走

`[设计已定，未实现]` `@nt-dpet/persona`

关系定位四选一，各自的默认称呼不同：

| 关系 | 默认称呼 |
|---|---|
| 妹妹 | 哥哥 |
| 伴侣 | 宝宝 / 乖乖 / 老公（「亲爱的」太正式，不进默认值） |
| 朋友 | 直呼名字或起外号 |
| 助手 | 老板（敬称，保持距离感） |

这是**默认值联动，不是硬绑定**：选了「伴侣」也可以手动改回别的称呼，人格文本只读最终值。猫娘浓度另有三档（清淡 / 标准 / 浓），与称呼互不影响。

### 3.4 日常对话不经过 agent loop

`[已实现]` `@nt-dpet/dialogue`

DSH 的 agent loop 为「执行任务」设计：规划、调工具、多轮修复。日常聊天不需要这些，走完整条链路既慢又贵，还会把对话写进会话体系。

所以聊天走一条独立轻通道：一条 system + 历史 + 本轮输入 → 流式返回。**不建 Session、不写会话日志、不发工具调用**。

**细节**：

- 只把 `text-delta` 透给界面，`reasoning-delta` 一律过滤——用户看到的是干净的正文，不会看到模型的自言自语
- 中断与失败分开处理：用户关窗产生的 `AbortError` 记作 `aborted`，真正的错误记作 `error`，两者在界面上不该长同一个样子
- 未知分片类型不抛错。上游新增分片不应该弄崩对话

这条路已实测：不建 Session 也能正常拿到回复，因此隐私约束不需要用功能来换。

### 3.5 隐私不是开关，是默认值

**三项固定动作**（不是可选项）：

1. **关闭会话日志上传**。上游 DSH 默认把会话日志随每次请求上传，内容包括消息全文、工具参数与结果、工作区路径；且 `DSH_TELEMETRY_DISABLED=1` 关不掉它。本项目在安装时写入关闭配置，**每次启动校验**，校验不通过则拒绝启动
2. **对话不建 Session**，从源头不产生会话日志
3. **界面不给隐私开关**。日志上传与使用统计固定关闭，界面上只显示「已固定关闭」。理由：日志上传一旦开过，关闭期间的内容会在重开时补发，「关掉就干净了」是错的——与其给一个让人误以为安全的开关，不如不给

### 3.6 界面：像 DSH，但内容换掉

`[已实现（静态壳）]`

三栏布局：左栏会话列表（按 QQ 号 / 群号分组）+ 对话/工作双视图切换，中间对话区，右栏「她的状态」（情绪五维、关系、最近记忆）。底部状态栏显示情绪文字描述与通道连接状态。

**细节**：

- 视觉严格遵循 Apple HIG：大留白、毛玻璃、系统字体、圆角卡片；字体单位只用 px / rem（禁 rpx）；主色 `#3D7CA8`
- 深浅色优先跟随系统，系统未提供时按日出日落切换；共四种主题模式
- 设置面板分七组（模型 / 她 / 外观 / 通道 / 隐私 / 开发者 / 关于），与「渐进式暴露」对应：简单用户只在第一层动手，其余用默认值就够
- **不许有假开关**。每一项都真的改到状态；没接后端的项显式标注「未接入」，而不是做一个点了没反应的开关——假开关比缺功能更糟
- 开发者模式的两条保护必须同时生效：先展开后果说明并二次确认，确认后立刻建还原点。只做其中一条等于没做

### 4.1 与官方 DSH 的隔离

安装 NT-Dpet **不修改用户已有的 DSH 环境**。隔离在四个层面同时生效：

| 维度 | 官方 DSH | NT-Dpet | 手段 |
|---|---|---|---|
| 数据目录 | `~/.dsh` | 自有 `dsh-home/` | `DSH_HOME` |
| 技能与指令 | `~/.agents` | 自有 `agents/` | `DSH_AGENTS_HOME` |
| profile | `desktop` | `nt-dpet` | `--profile` |
| 端口 | `3080` | `3180`（冲突时递增） | `--port` |
| 进程 | 官方 App | 独立子进程树 | 各自 spawn |
| Electron 单实例锁 | 官方 App 的 | 独立 `productName` | 应用标识不同 |

四条禁止事项（违反任一条即破坏隔离）：

1. 不写 `~/.dsh` 下的任何文件
2. 不写 `~/.agents` 下的任何文件
3. 不占用 `3080`
4. 不依赖官方 App 的进程存活

**唯一允许的跨目录读取**：首次启动时以只读方式检查 `~/.dsh/.credentials.yaml`，询问用户是否沿用已配置的密钥。用户确认后才复制到自有目录，**绝不回写**。

隔离已实测确认：在独立 `DSH_HOME` 下运行 CLI 后，该目录外无任何文件被创建。详见 `docs/ARCHITECTURE.md` §2.3。

### 6.3 在独立 DSH 环境中验证插件

以下流程不触碰用户已有的 `~/.dsh`：

```bash
BIN="/Applications/DeepSeek Harness.app/Contents/Resources/app/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js"
export DSH_HOME=/tmp/nt-dpet-probe/dsh-home

# 1. 从内置 web 模板创建独立 profile（无需先安装插件）
node "$BIN" --profile nt-dpet --from-default-profile web

# 2. 查看合成后的插件树，确认自己的 entry 已进入
node "$BIN" --profile nt-dpet --patch ./my.yml --dump-config

# 3. 启动（使用 --profile 时不要再写 app 名）
node "$BIN" --profile nt-dpet --patch ./my.yml --no-open --port 3180
```

三条实测结论：

- 启动日志中的 URL 带**随机 token**，默认绑定 `127.0.0.1`
- **插件加载失败不阻断启动**：只输出 `warning: 1 entry did not activate`。产品侧必须做激活数自检（见 §8.3）
- `--profile` 与 app 名不可同时出现，否则报 `too many arguments`

## 七、模型接入

### 7.1 配置方式

模型调用统一经 `dsh-llm` 服务，由 provider 适配器落地。**密钥不出现在任何配置文件里**：patch 只声明环境变量名，值由凭据 seam 在每次请求时解析。

以 OpenAI 兼容的本地网关为例：

```yaml
# cordis.patch.yml
- id: llm-pi-ai
  name: '@deepseek-ai/dsh-llm-pi-ai'
  config:
    providers:
      magpie:
        displayName: 本地网关
        api: openai-completions
        baseURL: http://127.0.0.1:3425/v1
        apiKeyEnv: MAGPIE_API_KEY
        models:
          - id: group/ntars
            name: 本地模型
            contextWindow: 1048576
            maxTokens: 384000
```

```bash
export MAGPIE_API_KEY=<密钥>
```

两条注意：

- 覆盖已存在的 entry 时**必须写 `id`**，否则报 `patch: id is required for non-insert patches`
- 手工声明的 provider 不会出现在 `ctx.llm.listProviders()` 中（该方法报告的是 GUI 可选目录），但 `ctx.llm.stream({ provider })` 照常可用

### 7.2 调用方式

`dialogue` 包内部即走此路径，也可由其他包直接调用：

```ts
const result = await dialogue.chat(
  { system: 提示词, history: 历史消息, input: 用户本轮输入 },
  { model: 'group/ntars', maxTokens: 300, reasoning: 'high' },
  (u) => { if (u.kind === 'text-delta') process.stdout.write(u.delta) },
)
// result: { text, stopReason: 'stop' | 'aborted' | 'error' | 'length', usage }
```

### 7.3 已验证的端到端结果

真实包（非测试桩）挂载在独立 profile 中，经本地网关请求：

```
[e2e] dialogue 服务: true | emotion 服务: true
[e2e] 用时 15196 ms
[e2e] 回复: "欢迎回来喵，主人～"
[e2e] stopReason: stop | usage: {"inputTokens":44,"outputTokens":6,"totalTokens":50}
[e2e] 流式增量条数: 6
[e2e] emotion.mood 写入后读出: 0.8
```

同一次挂载里，对话与情感两个服务在同一容器中互相可见、各自工作。

## 八、插件开发约定

### 8.1 包的必备文件

```
packages/<name>/
├── package.json          # 必须含 type: module、main、files、dsh.bundle.patch
├── cordis.patch.yml      # 挂载声明，必须用 insert 包裹
├── tsconfig.json
└── src/index.ts          # export name / export function apply(ctx)
```

`cordis.patch.yml` 的正确写法：

```yaml
- insert:
    - id: nt-dpet:core:emotion
      name: "@nt-dpet/emotion"
```

写成裸 entry（`- id:` 直接开头）**不报错、不警告、直接消失**。这是本项目最容易踩、最难发现的坑。

### 8.2 四条硬约束

1. **仅 ESM**：`@deepseek-ai/*` 为 ESM，CommonJS 会触发 `ERR_REQUIRE_ESM`
2. **必须声明 `inject`**：读取未声明的服务会抛 `cannot get property "X" without inject`，且**整个插件不激活**——不是某个属性读不到，是插件不存在
3. **entry id 全项目唯一**：命名规范 `nt-dpet:<组>:<名>`
4. **patch 必须用 `insert` 包裹**（见 §8.1）

### 8.3 启动自检

DSH 对插件加载失败采取软失败策略：服务照常启动，只有一行 warning。这在插件宿主里是合理宽容，在伴侣软件里不可接受——用户会看到界面正常，以为一切正常，直到「她怎么不理我」才困惑，而归因会落在产品本身。

因此每次启动须自检：

| 检查项 | 判据 | 不一致时 |
|---|---|---|
| entry 激活数 | 配置树 entry 数 == 实际激活数 | 界面横幅告警，列出未激活 id 与原因 |
| 隐私开关 | `session-log-deepseek` 与 `plugin-package-inventory-deepseek` 均为 `false` | **拒绝启动**，给出修复指引 |
| 关键包 | `emotion` / `memory` / `dialogue` / `persona` 均在激活列表 | 降级为只读，并明示缺失能力 |

隐私一项之所以是拒绝启动而非警告：静默放行等于把聊天全文传出去。设计依据见 `docs/ARCHITECTURE.md` §4.4。

### 9.1 界面壳

位于 `packages/ui/web/`，可直接在浏览器中查看：

```bash
cd packages/ui/web && python3 -m http.server 8731

node packages/ui/web/test/smoke.mjs
```

界面为**纯静态壳**，数据来自 `js/data.js` 的演示数据，未连接任何后端。所有开关均绑定真实偏好状态，未接入后端的项显式标注「未接入」。

冒烟测试用调试协议做真实点击，覆盖偏好写入、DOM 联动、面板开关、开发者模式的两条保护、日志滑块位移，共 14 项。

```bash
python3 -m http.server 8920
# http://127.0.0.1:8920/
```

介绍页位于仓库根，便于静态托管平台直接取用入口文件。页面「界面」一节使用界面壳真实截图（`assets/ui-*.png`），按 `prefers-color-scheme` 自动切换深浅两版；界面变更后应重拍，不得手动修图。

## 十、隐私与数据

- 对话与记忆默认全部存放在本机
- 上游 DSH 默认随每次模型请求上传会话日志，且环境变量无法关闭该行为；本项目强制关闭并每次启动校验（§3.5）
- 对话通道不创建 DSH Session，因此不产生会话日志
- 用户资产（人格、凭据、日记、账本、还原点）存放于 `user/` 目录，与 `dsh-home/` 分离——避免 profile 重建时把「她的一生」一起清掉
- 导出的数据可带走；卸载后本机不残留

详见 `docs/ARCHITECTURE.md` §2.3、§16。

### 11.1 移动端桌宠（占位）

`packages/pet-mobile/` 已留出位置，**默认禁用**，无任何实现。

三端能力差异是结构性的，不能共用一套渲染：

| 平台 | 能否桌面常驻立绘 | 可行形态 |
|---|---|---|
| 安卓 | 可以（`SYSTEM_ALERT_WINDOW`） | 真·桌宠：常驻、可拖动、可交互 |
| 苹果 | 不可以（系统不开放第三方全局悬浮窗） | 灵动岛 / 实时活动 / 小组件 + 应用内形象 |
| 鸿蒙 | 待确认 | 服务卡片 / 万能卡片，接近苹果，需单独适配 |

因此移动端不采用「桌面立绘」形态，而以「通知里的她、锁屏一行字、小组件上的状态」为主：桌面端的优势是一直看得见，移动端做不到，硬追只会做成耗电的悬浮球。**移动端不做桌宠，做她留在你手机上的痕迹。** 该判断需在产品层面确认后再实现，详见 `docs/ARCHITECTURE.md` §11.4。

## 十四、风险声明

**账号风险**：接入个人 QQ 号（NapCat 通道）可能导致**永久封号**，并可能波及所在群聊与关联账号。软件无法保证账号安全，风险由使用者承担。官方机器人通道无此风险，是无封号顾虑时的推荐选择。

**AI 内容标识**：本软件不代替使用者添加 AI 生成内容标识。在公开平台使用本软件输出时，使用者依《人工智能生成合成内容标识办法》（2025 年 9 月 1 日施行）负有标识义务。

**隐私**：详见 §10。上游默认上传会话日志的行为已由本项目强制关闭并校验，这是本项目优先级最高的一项修复。
